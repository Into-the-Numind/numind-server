# RAG 内核优化 · 真实数据评估结论（iDriveCareer 真实生产 KB）

> 2026-06-18。把"测的准不准"做实之后的最终结论。所有数字在**莫小派真实客户 iDriveCareer 的完整生产 KB**上、用**真文档合成 + 真实 query 挖掘 + 对抗校标**的 68 题黄金集量出。
> **一句话结论：真实数据基本验证了现有内核已接近最优，并排除了几个诱人但有害/无用的改动——本轮不向生产内核引入任何新改动。**

## 0. 先纠了两个根本前提（否则全是白测）
1. **真实 RAG 流量在 SalesRAG，不在 chatbot**。prod 高流量 chatbot(1/2/4/9/11，几百问)根本没挂 KB；挂 KB 的 chatbot 只有 2 个(18 问 + 0 问)。莫小派真实知识库问答走 **SalesRAG**(sales_message，195 条真实提问)。
2. **两条路检索配置不同**：chatbot=0.6 阈值+不改写；SalesRAG=**0.3 默认阈值 + 已经在改写**(销售意图改写器)。先前在 chatbot 路径上得的"保持 0.6 / 加改写 / intent_declarative 完胜"结论**不适用真实路径**——它们是小/合成语料的产物。

## 1. 可信尺子怎么建的
- **语料**：iDriveCareer(留学/海外职业咨询，莫小派子账户 user 350)完整真实 KB，13 篇/82 chunk(公司介绍/客服问答库FAQ/案例库/观点库/产品/各类会员合同)，从 prod 向量库原样复制进 dev(user_id=350 隔离，零碰撞)。
- **题**：68 题 = 真文档合成 44(有明确出处) + 真实 query 挖掘 14 + **硬负例 10**。每条标签经独立 judge 对照全集对抗校标、丢 7 条歧义。硬负例是"在域(留学/职业/会员)但 iDC 库答不了"的真问题——多为**莫小派其它产品线**(小红书IP陪跑/职场跃迁/房产保险IP)，这是真实场景里最危险的一类(答错=拿别家产品话术答 iDC 客户)。

## 2. 四个杠杆的真实数据结论

### ① rerank 阈值 → **0.3 最优，无需改动**（SalesRAG 现用 0.3，已验证最优）
| T | in-KB recall | MRR | 库外拒答 |
|---|---|---|---|
| raw(无阈值) | 0.966 | 0.904 | 0.20 |
| **0.30** | **0.845** | **0.796** | **1.00** |
| 0.40 | 0.810 | 0.770 | 1.00 |
| 0.60(chatbot 用的) | 0.759 | 0.718 | 1.00 |
0.3 是**让库外拒答达到 1.0 的最低阈值**(含 10 条硬负例全部正确拒答)，再往上只丢召回不增拒答。**验证了 SalesRAG 的 0.3 默认正确**；chatbot 的 0.6 在真实数据上偏高(白丢 ~0.09 召回)。注：先前 chatbot 合成语料上"保持 0.6"是语料太窄+只有易判负例造成的假象，真实数据已纠正。

### ② 混合检索(BM25+向量 RRF) → **不值得做**
vector-only recall 0.966 / MRR 0.904；hybrid recall 0.966(**持平**) / MRR **0.85**(↓) / nDCG 0.876→0.852(↓)。向量+重排已主导，BM25 融合只加噪声、拉低排序质量。**省掉一块工程**。

### ③ HyDE → **绝不能上**（确定性安全泄漏）
recall 0.914(超基线)但**库外拒答崩到 0.6**。q59→doc26@0.615 / q61→doc50@0.55 / q63→doc50@0.35 经 raw-vs-HyDE 各三连跑确认是 HyDE **确定性**引入的硬泄漏(分数远离 0.3 边界，非后端噪声)。HyDE 对"库里没有"零感知，会自信编出像 iDC 自家产品的答案，把别家产品问题拉进库内。对 B2B2C 场景=跨产品线串答事故。

### ④ 查询改写(intent-declarative / neutral-expansion / multi-query) → **本轮都不上**
| 策略 | recall | MRR | 库外拒答 |
|---|---|---|---|
| baseline | 0.845 | 0.796 | **1.0** |
| intent-declarative | 0.828 | 0.753 | 1.0(抖) |
| neutral-expansion | 0.931 | 0.848 | 0.8–1.0(抖) |
| multi-query | 0.983 | 0.886 | **0.5** |
**深层发现(只有真实硬负例才暴露)**：任何能提升 in-KB 召回的改写，**同时抬高了"在域但库外"硬负例的 rerank 分**——因为它们和 iDC 是同一个域。固定单阈值下二者大量落在 0.30~0.35 同一带，**召回↑必然伴随库外拒答↓**。所以改写不是不能提召回(能，多查询甚至到 0.983)，而是**在固定阈值上提召回 = 牺牲防幻觉**。先前合成语料(易判负例)上 intent_declarative"完胜"正是因为没有硬负例。**这就是用真实数据的价值。**

## 3. 真正的瓶颈与下一步方向（架构级，非本轮）
瓶颈不是检索技术，是**单一固定阈值分不开"库内"和"在域但库外"**。要既提召回又守拒答，需要**把"答得了吗(answerability/topicality)"做成独立于召回阈值的二级门**(检索后 LLM 域判定 / 双阶段)。这是个架构改动，留作下一步独立项目；它是唯一能突破"召回 vs 拒答"死结的方向。

## 4. 运营发现
dev 的 rerank 后端是 **dmxapi 免费档 bge-reranker-v2-m3-free**，在持续评估负载下**会被限流/打挂**(返回 0 chunk，强非确定)。dev 未配 prod 那套 rerank 级联兜底(prod 有 dmxapi→ali 兜底)。**建议**：要可靠跑评估/保障线上检索质量，dev 应补上 rerank 兜底级联或用稳定档位。

## 5. 本轮决策（ship 什么）
- **生产内核：不引入任何新改动**。0.3 阈值已最优(SalesRAG 现用)；混合检索不做；HyDE 不上；查询改写本轮不上。
- chatbot-query-rewrite(③，先前 flag-OFF 上 dev)：**保持 OFF**。真实数据证明查询改写在有硬负例时破坏拒答，先前它"完胜"是合成语料假象。
- **交付的是知识 + 工具**：可信的真实数据评估集(golden_idc.yaml)+ 复现方法 + 本报告的"别做这些"结论。下一步要动就动架构级的 answerability gate。
