# 飞书授权链接刷新后恢复原任务的设计

## 决策

采用“原子替换后放行、失败可补偿重试”方案：在同一个数据库事务内，以旧会话标识为前置条件，同时作废旧会话、创建替换会话、更新原任务的持久化恢复摘要和账号等待状态。事务提交后才启动并放行新会话的本地授权工作器。若新工作器未能产生可用链接，则原子恢复旧绑定；即使该恢复因短暂存储故障未完成，用户在原卡片上重试也能安全地完成恢复并取得新链接。

这延续现有的安全模型：浏览器只提交任务 ID 或不透明会话 ID，恢复时仍只接受任务摘要中精确绑定、且属于同一用户、同一代际、同一任务、同一授权阶段的会话。

## 方案比较

### A. 安全重绑后放行（采用）

刷新时原子地替换旧会话和原任务摘要，再启动新工作器。恢复流程保持原有的“只按任务摘要找会话”规则。

- 优点：任务重启后仍能恢复；不扩大授权查找范围；不会在数据库写入失败时留下“任务指向已作废会话”的半完成状态；与初始授权的“先持久化、后激活”顺序一致。
- 代价：需要一个受用户、代际、任务状态和旧会话标识共同约束的事务性存储操作。

### B. 恢复时查找同任务最新会话

不更新任务摘要，恢复时改为扫描同任务的最新待处理会话。

- 优点：代码表面上更少。
- 缺点：丢失持久化的精确会话绑定，重启后状态不完整，也使授权边界更难审计。拒绝。

### C. 禁止刷新链接

让链接过期后要求用户重新发起整个任务。

- 优点：不需要修改恢复状态。
- 缺点：违背链接刷新功能和用户预期，且不能修复现有 500。拒绝。

## 数据流

1. 用户请求刷新仍待完成的授权会话。
2. 生命周期服务只接受与原任务摘要精确绑定的旧会话。
3. 存储层在一个事务内锁定当前账号、旧会话和任务；同时创建同一任务的替换会话、作废旧会话、更新任务摘要中的会话标识和过期时间，并写入对应的账号等待状态。
4. 事务失败会整体回滚，旧会话和原任务绑定保持不变；不会向浏览器返回新链接。
5. 事务提交后才停止旧工作器、启动并放行新工作器。手动连接会话不经过此路径。
6. 若新工作器在返回链接前失败，存储层在另一受同样条件保护的事务内作废替换会话、恢复旧会话和旧任务摘要；成功后才停止本地替换工作器并清除其内存链接。
7. 如果第 6 步的存储写入暂时不可用，原卡片保留的旧会话 ID 可再次请求刷新。它只能修复同一任务摘要精确指向的替换会话，且该替换会话没有有效工作租约时才允许继续。
8. 用户点击“我已完成，继续”时，现有恢复逻辑从更新后的摘要取得新会话。会话仍待完成则正常返回等待状态；完成后仍由唯一的共享调度器恢复原 Agent 任务。

## 错误与并发规则

- 原子替换必须同时限定用户、当前代际、任务 ID、等待状态、旧会话 ID、授权阶段和申请权限；条件不匹配即整体回滚，不退化为查找任何活跃会话。
- 只有事务提交成功才激活替换会话。失败时不暴露成功结果，也不得让未绑定会话完成原任务。
- 恢复旧绑定时也必须重新锁定账号、旧会话、替换会话和任务摘要。替换会话仍有未过期租约时，旧卡片必须被拒绝，不能停止或覆盖正在工作的最新授权。
- 本地停止替换工作器只能发生在恢复旧绑定的事务提交之后；事务失败不产生本地取消副作用。
- 不保存或记录临时 URL、设备码或凭据；仅保存现有的会话 ID、阶段和过期时间。
- 正常刷新后的立即继续必须返回任务的等待状态，不能产生内部错误。

## 测试

1. 先写失败回归测试：刷新一个任务绑定的待处理会话后，任务摘要必须指向新会话，且新会话必须被激活。
2. 在同一测试中立即执行“我已完成，继续”，验证返回等待状态且不调用重复调度。
3. 覆盖事务性替换失败：旧会话和原任务摘要保持不变，替换会话不落库。
4. 覆盖替换工作器启动失败：旧卡片可再次刷新；覆盖补偿存储暂时失败后，旧卡片仍可自我修复。
5. 覆盖旧卡片与新工作器抢租约的竞态：旧卡片既不能改写摘要，也不能取消新工作器。
6. 运行飞书业务包测试、存储测试、全仓测试和 Go lint。
