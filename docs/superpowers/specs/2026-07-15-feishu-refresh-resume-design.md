# 飞书授权链接刷新后恢复原任务的设计

## 决策

采用“安全重绑后放行”方案：刷新链接生成替换会话后，服务端以旧会话标识为前置条件，将原任务的持久化恢复摘要替换为新会话的标识和过期时间；写入成功后才激活新会话的本地授权工作器。

这延续现有的安全模型：浏览器只提交任务 ID 或不透明会话 ID，恢复时仍只接受任务摘要中精确绑定、且属于同一用户、同一代际、同一任务、同一授权阶段的会话。

## 方案比较

### A. 安全重绑后放行（采用）

刷新后持久化地更新原任务摘要，再激活新工作器。恢复流程保持原有的“只按任务摘要找会话”规则。

- 优点：任务重启后仍能恢复；不扩大授权查找范围；与初始授权的“先持久化、后激活”顺序一致。
- 代价：需要增加一个受用户、代际、任务状态和旧会话标识共同约束的存储更新操作。

### B. 恢复时查找同任务最新会话

不更新任务摘要，恢复时改为扫描同任务的最新待处理会话。

- 优点：代码表面上更少。
- 缺点：丢失持久化的精确会话绑定，重启后状态不完整，也使授权边界更难审计。拒绝。

### C. 禁止刷新链接

让链接过期后要求用户重新发起整个任务。

- 优点：不需要修改恢复状态。
- 缺点：违背链接刷新功能和用户预期，且不能修复现有 500。拒绝。

## 数据流

1. 用户请求刷新仍待完成的授权会话。
2. 授权服务使旧会话失效，并创建同一任务的替换会话及临时飞书链接；新工作器保持等待状态。
3. 生命周期服务验证替换会话与旧会话属于同一用户、代际、任务和授权阶段。
4. 存储层使用旧会话标识与当前等待状态作条件，原子更新任务的恢复摘要为替换会话标识和过期时间。
5. 更新成功后调用现有激活接口放行新工作器；若重绑失败，不向浏览器返回可用的新链接，工作器保持取消或等待安全退出。
6. 用户点击“我已完成，继续”时，现有恢复逻辑从更新后的摘要取得新会话。会话仍待完成则正常返回等待状态；完成后仍由唯一的共享调度器恢复原 Agent 任务。

## 错误与并发规则

- 重绑必须同时限定用户、当前代际、任务 ID、等待状态和旧会话 ID；条件不匹配即失败，不退化为查找任何活跃会话。
- 只有重绑成功才激活替换会话。失败时不暴露成功结果，也不得让未绑定会话完成原任务。
- 不保存或记录临时 URL、设备码或凭据；仅保存现有的会话 ID、阶段和过期时间。
- 正常刷新后的立即继续必须返回任务的等待状态，不能产生内部错误。

## 测试

1. 先写失败回归测试：刷新一个任务绑定的待处理会话后，任务摘要必须指向新会话，且新会话必须被激活。
2. 在同一测试中立即执行“我已完成，继续”，验证返回等待状态且不调用重复调度。
3. 覆盖重绑失败：不激活替换会话，也不改变原任务到无关会话的绑定。
4. 运行飞书业务包测试、存储测试和 Go lint。
