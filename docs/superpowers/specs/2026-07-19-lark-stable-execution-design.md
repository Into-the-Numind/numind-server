# 飞书 Agent 稳定执行设计

Generated by NDF S2 on 2026-07-19  
Status: APPROVED（产品负责人已确认方案 B，并授权自动执行到 Dev）

## 1. 问题定义

当前平台把 `lark_skill_read` 生成的长 HMAC receipt 交给 LLM，再要求 LLM 原样复制到 `lark_execute`。receipt 既不是用户授权，也不能证明 Agent 理解了技能；它只证明同一 run 读过技能。LLM 在真实 Dev 任务中两次抄错 receipt，平台在 1ms 内拒绝命令，飞书从未被访问。随后 Agent 把内部策略拒绝误判成连接或权限故障。

同一类可修正 soft error 会产生 `tool_call_error` 和红色“执行出错”，即使 Agent 随后换成正确命令并成功。用户看到的是多次失败后偶然成功，而不是系统在内部调整。

## 2. 目标与非目标

### 2.1 目标

1. Agent 只提交受控业务 argv 和可选 JSON stdin，不携带平台内部授权票据。
2. 平台从当前 HTTP/Agent 上下文和命令 catalog 派生用户、domain、risk、scope、确认与幂等条件。
3. 技能读取只提供使用说明和受控 references，不再产生模型可见 receipt。
4. 模型收到稳定、准确、不可泄密的错误 code、message、recoverable/retryable 提示。
5. 可恢复 soft error 在 Agent 时间线中显示“正在调整执行方式”，真正终止错误才显示红色。
6. 老对话携带的 `skill_receipts` 在过渡期继续被 decoder 接受但完全忽略。

### 2.2 非目标

- 不新增飞书能力，不开放 IM、Drive 写入或本地 shell。
- 不新增 HTTP API、数据库 schema 或外部服务。
- 不升级 lark-cli；官方当前可用版本与项目固定版本的升级另立需求，避免把协议修复和供应链升级混在一个变更。
- 不自动重试已经开始且结果未知的写操作。

## 3. 安全不变量

以下条件在 receipt 移除前后必须相同：

1. `user_id` 只来自服务端 context，模型不能提交。
2. 每个操作只使用该 user 当前 generation 的加密 CLI HOME。
3. `CommandCatalog.Normalize` 是唯一业务命令入口；未知 domain/action/flag、IM、auth/config/whoami/shell 均在访问飞书前拒绝。
4. domain、risk、required scopes、`--as user`、`--format json`、`--yes` 只由服务端 catalog 决定。
5. 写/高风险命令先做只读 scope preflight；缺权限进入现有授权卡片和 durable resume。
6. 高风险确认、执行 gate、加密 operation、idempotency key、generation fence 保持不变。
7. 写操作一旦 business_started 且结果未知，状态为 unknown，不自动重放。
8. 日志和模型输出不得包含 token、HOME、receipt、完整内部错误或用户文档正文。

receipt 的删除不会削弱这些不变量，因为 receipt 从未绑定飞书账号、权限、资源或写入结果。

## 4. 后端协议

### 4.1 `lark_execute`

新模型 schema：

```json
{
  "type": "object",
  "properties": {
    "argv": { "type": "array", "minItems": 1, "items": { "type": "string" } },
    "stdin_json": {}
  },
  "required": ["argv"],
  "additionalProperties": false
}
```

服务端 decoder 为滚动升级兼容额外接受旧字段名 `skill_receipts`，但不解析、不验证、不复制到安全决策。其他额外字段继续严格拒绝。一个可选前导字面量 `lark-cli` 继续安全剥离；其余 argv 交给 catalog。

`ExecuteRequest.SkillReceipts` 在兼容期可保留为废弃字段，Agent adapter 不再写入，`FeishuOperationService.Execute` 不再调用 `VerifyRequired`。receipt signer/verifier 暂时保留为内部兼容代码，不再位于执行授权链，后续可以独立删除而不影响协议。

### 4.2 `lark_inspect`

`connection` 仍只接受 mode。`command` 新 schema 只要求 mode+argv；旧 `skill_receipts` 同样接受但忽略。command inspection 仍由 catalog、当前用户连接和 scope preflight 决定，永不执行业务命令。

### 4.3 `lark_skill_read`

输出删除 `receipt`。保留 `skill/path/hosted_policy/content/references/cursor/cli_version`。托管规则删除所有“复制 receipt”“换 exact receipts”文案，改为：

- 读取技能是为了命令说明；
- 直接调用 Docs/Base/Wiki/Drive 业务命令；
- 平台负责身份、权限与恢复；
- title discovery 和安全停止规则保持不变。

## 5. 结构化错误与恢复语义

`larkWorkspaceSoftError` 返回固定、审阅过的字段：

```json
{
  "error": "ERROR: <固定中文说明>",
  "code": "command_rejected",
  "recoverable": true,
  "retryable": false
}
```

- `error` 保留给现有 Eino soft-error detector 和 LLM。
- `code` 只取固定 enum，不包含 argv/provider 原文。
- `recoverable=true` 表示本次 tool result 已安全返回给模型，模型可以在预算内修正，不代表外部操作成功。
- `retryable=true` 仅表示同一输入的暂时性平台重试被允许；命令修正使用 recoverable，不滥用 retryable。

分类：

| code | recoverable | 含义 |
|---|---:|---|
| `invalid_execute_input` | true | 模型字段形态错误，可修正一次 |
| `command_rejected` | true | catalog 拒绝，飞书未访问，可修正一次 |
| `correction_exhausted` | false | 修正预算耗尽，停止 |
| `identity_unavailable` | false | 服务端身份上下文无效 |
| `workspace_unavailable` | false | 安全依赖不可用，不盲目重试 |
| `invalid_result` / `invalid_wait` | false | 平台合同异常 |
| `invalid_inspect_input` / `inspect_rejected` | true | 检查参数可修正 |
| `inspect_unavailable` | false | 检查依赖不可用 |
| `execution_stopped` | false | 先前结果禁止继续 |

业务操作已经返回的 `OperationFailure` 继续使用现有 `category/retryable/operation_state`，不被 soft-error 分类覆盖。`rate_limited/temporary` 只按已有结构化结果和预算重试；unknown write 永远停止。

## 6. Agent 事件与前端状态

### 6.1 事件合同

`softToolErrorMessage` 扩展为读取可选 `recoverable`。只有显式 `recoverable=true` 的 soft result：

- polling narration 写 `progress`，固定文案“正在调整执行方式”；
- SSE `tool_call_error` 增加 `recoverable: true`，保留 tool_call_id 和 duration；
- Go error 仍为 nil，LLM 能继续修正。

没有该字段的旧 soft error、`recoverable=false`、真实 Go error：维持 `error` narration 和 `tool_call_error`，显示红色。

### 6.2 前端渲染

`ToolCallErrorPayload` 增加可选 `recoverable?: boolean`。store 收到：

- recoverable=true：把 tool group 状态设为 `progress`，message=`正在调整执行方式`，显示品牌色 spinner；不保存/显示技术错误。
- 其他：状态设为 `error`，message=`执行出错`，红色 alert。

当同一 run 后续完成/失败，现有 `finalizeToolGroups` 将仍在 progress 的步骤随 run 终态收束。真实终止 error 已经是 terminal state，不会被完成状态覆盖。轮询 narration 因后端直接使用 progress/error，同样行为，无需前端猜测。

授权、确认属于 pause，不是 error，继续使用现有 external action 卡片。

## 7. 数据流

```text
用户指令
  -> Agent 读取技能说明（无 receipt）
  -> lark_execute(argv, stdin_json?)
  -> 服务端注入 current user/run/tool-call/idempotency
  -> CommandCatalog.Normalize
  -> 当前用户 Feishu account + generation
  -> scope preflight / auth card / confirmation（按需）
  -> encrypted operation + durable execution gate
  -> pinned lark-cli business command
  -> structured result
  -> Agent final answer
```

不存在 Agent -> receipt -> verifier 这条链。

## 8. 测试策略

### 8.1 客户 RED

后端首先提交失败测试，复现：技能读取成功后，合法 Drive title search 不提供 receipt 或提供错误旧 receipt，当前代码在 executor/operation 前拒绝。期望新合同能到达 executor，同时 `auth/status` 仍拒绝。

前端首先提交 Playwright 失败测试，构造 `tool_call_error(recoverable=true)` 后继续成功的 SSE；当前页面会显示红色“执行出错”，期望显示“正在调整执行方式”且无红色 error class。另测 hard error 仍红。

### 8.2 后端回归

- schema 不再宣传/要求 receipt；legacy field 被忽略。
- skill output 不含 receipt，policy 不含 receipt 指令。
- operation/inspection 不调用 verifier，但 catalog/identity/scopes 仍调用。
- forbidden commands、cross-user、generation、idempotency、unknown write 全部保持。
- structured error code 与 recoverable 固定映射。
- adapter soft recoverable narration/SSE 与 hard error 分流。

### 8.3 前端回归

- Vitest 覆盖 recoverable/hard payload 到 aggregate 状态。
- AgentToolCallItem 的 progress/error 图标和文案。
- Playwright 覆盖一次 recoverable 尝试后成功，以及 hard terminal error。
- lint、type-check、现有 Agent streaming 测试。

## 9. 发布与回滚

先合并/部署后端，再合并/部署前端。后端兼容旧前端；前端的 optional 字段兼容旧后端。回滚前端不会影响执行安全；回滚后端会重新要求 receipt，因此只在新旧 Agent schema 同时回滚时执行。Dev 验收包括：标题读取、文档创建/更新、Base、Wiki、授权恢复、禁止命令与页面无假红错。

## 10. 成功标准

- 相同合法飞书指令在任意 Agent、新会话、服务重启或多实例下不依赖进程内/模型内票据。
- 用户可恢复过程不出现红色“执行出错”。
- 禁止命令和跨账号访问在外部调用前失败。
- 写操作未知结果不重试。
- 全量质量门通过并部署 Dev 健康。
