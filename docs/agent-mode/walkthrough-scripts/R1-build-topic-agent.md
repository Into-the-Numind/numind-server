# R1 实战：把"找选题 Agent"真建出来

> R0 裁决：R1 从"UI 走查"改为实战。一仗四得：CAP-1 能力探针 / 配置端走查 / design-baseline 校准 / 给莫小派的首个交付物雏形。
> 参与：用户 + AI（dev 环境，父账户）。预计 60-90 分钟。

## 目标任务（验收锚点）

> 给一个具体定位的小红书账号（现场定，如"教瑜伽馆主获客的账号"），让 agent 产出 **10 个爆款选题，每个附带：原始爆款依据（出处/数据）+ 移植改编建议**。

成功判定（CAP-1 探针结论从这里出）：
- **A 级**：≥5 个选题用户认为"能直接拿去拍"，且依据是真实近期爆款（非编造）→ 现有能力够，CAP-1 关闭
- **B 级**：选题方向对但依据泛泛/过时（Tavily 搜不到小红书墙内真实数据）→ CAP-1 立项补能力（候选：沙箱内浏览器自动化 / 第三方小红书数据源接入），列为上线阻断候选
- **C 级**：产出基本不可用 → 回到方法论本身（喂给 agent 的方法论不够可执行）+ 能力双查

## AI 的轮前准备（用户不参与）

- [ ] dev 部署核验（web 5419d0f / server HEAD，容器 sha 比对防 TCR silent-old）
- [ ] from-scratch 创建路径冒烟（修复后 422 应消失）
- [ ] **CAP-1 预探针**：AI 先用 dev 上的 agent 跑一次"搜小红书爆款选题"，预判 Tavily 对小红书内容的可达性，R1 现场不浪费用户时间在已知死路上
- [ ] 准备方法论注入路径：custom_skill_body 编辑未实现（v1 必修项未落地）前，确认现阶段可用注入方式（问卷生成 / skill 绑定 / DB 直写兜底）

## 现场流程

1. **口述粗版方法论（10 分钟）**：用户把自己理解的"找选题"打法口述（正式版等访谈莫小派专家后替换）。AI 现场整理成方法论文档草稿。
2. **建壳（≤5 分钟，计时！）**：用户亲手走 from-scratch 问卷建 agent。**计时 + 记录每个让你停顿/困惑的点**——这就是配置端走查，每个停顿都是 D/B 候选。顺便裁问卷：哪些题对"建壳"多余，哪些缺。
3. **注入方法论**：AI 协助把第 1 步的方法论灌进 agent（过程中暴露的工具缺口记录）。
4. **试跑真任务**：父账户在聊天页对 agent 下达目标任务，全程观察：工具调用是否合理、过程旁白是否可懂、产出质量。
5. **评级与裁决**：按 A/B/C 评级 → CAP-1 结论；D/B 类条目过一遍，当场定级。
6. **专家视角预演**：假设莫小派专家此刻坐在旁边，5 分钟内他能看懂并提出修改吗？哪里会卡？

## 产出

- D/B 类条目 → launch-backlog
