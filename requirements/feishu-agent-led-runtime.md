# 飞书 Agent 主导运行时

## 来源
- 提出人：产品负责人
- 提出日期：2026-07-18

## 需求描述
平台允许用户搭建多个 Agent。每个 Agent 都应像 Codex 使用完整工具一样，能够根据飞书业务目标选择 Docs、Base、Wiki、Drive 命令，看到可行动的结构化结果，并在连接或权限不足时继续原任务；平台只负责当前用户身份、凭证隔离、业务边界、用户授权和写入幂等。

当前实现把飞书 CLI 包在逐命令、逐错误形态的后端编排中。固定版本 CLI 返回一种未登记的合法结构时，后端会把真实的缺权限降级为 `failed/unknown`，Agent 失去判断依据并盲目换参数重试。Dev run 220/221 的 Docs update 已证明这一问题：官方命令正确，真实原因只是缺少 `docx:document:write_only`。

## 业务目标
- 同一用户的所有 Agent 共用该用户长期保持的飞书连接，不按 Agent 重复配置。
- Agent 主导业务命令选择和错误后的下一步；平台不再为每种业务错误写一条专用工作流。
- 读操作保持执行优先；写操作在真正调用飞书写接口前做只读权限预检。
- 缺权限时自动显示授权卡，完成后只执行一次原写操作。
- Docs、Base、Wiki 的创建、读取、更新走同一运行时机制；Drive 保持只读发现；IM 继续不开放。

## 优先级
最高

## Triage
- 推荐轨道：Standard
- 分类理由：不改 DB、不新增 HTTP API、不引入新外部服务；但涉及 Agent 工具、权限预检、授权恢复和写入幂等，影响文件超过 3 个且属于高风险权限逻辑。
- 人类决定：确认采用“Agent 主导、平台加护栏”的 B 方案，并要求快速但不减质量。

## 成功标准
- Agent 获得结构化、可行动的飞书结果，而不是笼统“执行出错”。
- 写权限缺失在业务写入开始前被发现；授权完成后实际写入次数严格为 1。
- 未知写入结果继续停止且不可自动重试。
- 同一机制覆盖 Docs/Base/Wiki 现有 CRUD 命令，不为每个命令单独增加权限分支。
- 多 Agent/多用户隔离、断线恢复和现有授权卡行为不退化。

## 非目标
- 任意 shell 或任意 OpenAPI 执行。
- Drive 写入、IM、联系人、日历等新业务域。
- 按 Agent 保存飞书账号或凭证。
- 新数据库表、新 HTTP API、新前端页面。
