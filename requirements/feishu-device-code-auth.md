# 飞书分步用户授权与原任务恢复

## 来源
- 提出人：Michael（产品/创始人）
- 提出日期：2026-07-16

## 需求描述
用户已经通过飞书官方页面创建个人自建应用，但 Agent 首次执行飞书文档操作时仍然失败。真实 dev 运行显示：账号停留在 `waiting_user_auth`，服务端以旧的阻塞方式执行 `lark-cli auth login --json --scope ...`，等待 30 秒仍拿不到授权链接后终止；Agent 最终只收到无细节的 `feishu_operation_failed`。

固定版本 `lark-cli 1.0.68` 的 Agent 授权协议是分步交互：先以非阻塞方式取得飞书官方授权链接和后续恢复凭据，用户在飞书完成授权后，再继续完成认证。现有系统必须按这个真实协议编排，不能再假设一条 CLI 命令会先输出链接、然后在同一个进程里等待用户完成。

同时，普通 Agent 沙箱不拥有服务器为当前用户保存的加密飞书 HOME。Agent 不应通过 `bash_exec` 执行 `lark-cli auth status` 或飞书业务命令；飞书认证判断和命令执行必须由用户隔离的连接编排器与 `lark_execute` 完成。

## 业务目标
用户提出“创建飞书文档”等任务时，如果缺少所需用户授权：

1. 有数立即展示可操作的飞书官方授权卡片，不出现 30 秒空等或泛化内部错误；
2. 用户完成授权并回到有数后，系统继续同一个授权会话并自动恢复原任务；
3. 原任务成功时直接返回文档结果，用户不需要刷新页面、重新发送 Prompt 或重新创建个人应用；
4. 授权成功后连接状态持久保持，后续 Docs、Base、Wiki 操作只在新增权限或凭据失效时再次引导授权；
5. 失败、过期、取消和权限拒绝都返回明确、可恢复且不泄露凭据的状态。

## 验收条件
1. 客户回归测试先复现当前行为：阻塞式 `auth login --json` 无法在 30 秒窗口提供 URL，operation 失败且账号停留在 `waiting_user_auth`。
2. 新流程第一阶段使用与固定 `lark-cli 1.0.68` 一致的非阻塞协议，可靠解析官方授权 URL 和不透明恢复凭据，并立即结束启动进程。
3. 恢复凭据仅存在于当前用户、当前应用 generation、当前 operation 和当前授权 session 的安全边界内；不得返回前端、写入日志或被其他用户/session 使用。
4. 用户点击“我已完成，继续”后，系统使用精确绑定的恢复凭据完成第二阶段认证；重复点击、过期卡片和并发确认不得启动第二次写操作。
5. 认证成功后，账号从 `waiting_user_auth` 进入 `connected`，加密 HOME 正确持久化，原 operation 自动恢复且只执行一次。
6. 使用真实等价的 CLI fixture 验证完整分步协议；测试不得继续伪造“`--json` 阻塞进程会立即输出 URL”的旧行为。
7. Agent 系统指引明确禁止用普通 `bash_exec` 检查或操作飞书；缺权限时只调用 `lark_execute`，由确定性编排器返回授权卡片。
8. dev 真实验收：发送“创建飞书文档”后完成一次官方用户授权，原请求自动创建文档；随后再次创建文档不再要求相同权限，也不出现 Internal server error、空白等待或必须刷新页面的情况。

## 备注
- 不重新设计“个人自建应用”产品模型，也不新增独立飞书 Agent。
- 不扩大一期能力范围：Docs、Base、Wiki 创建/读取/更新；IM 仍不包含。
- 当前真实账号已有个人应用配置，修复必须复用该应用，不要求用户重复创建。
- `device_code` 等名称是 CLI 协议概念，具体 JSON 字段和有效期必须在 S1/S2 通过固定版本真实输出确认后锁定。
