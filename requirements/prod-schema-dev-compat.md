# Dev 数据库历史结构兼容

## 来源

- 提出人：Dev → Prod 全量上线验收
- 提出日期：2026-07-30

## 需求描述

Prod 升级包在 S6 Dev 真库只读 preflight 中发现 5 个阻断项。Dev 功能本身可用，
但它经历过多轮增量迁移，部分结构与“从零一次建成”的 Prod 目标结构在字段顺序、
新附件字段可空性、历史智能体状态和飞书外键上存在差异。

修正必须让同一份升级包既能安全处理 Prod 的缺失结构，也能兼容 Dev 已有历史结构，
且不能为了通过检查去覆盖或清洗用户、积分、附件、智能体或飞书业务数据。

## 业务目标

1. Dev 真库可以完成备份、preflight、双次 migration 和 verify 演练。
2. Prod 缺失的新表/字段仍按最终目标结构创建。
3. Dev 已运行功能的 45 条附件、389 条智能体运行和飞书工作区记录保持原值。
4. 飞书证明表缺失的外键在确认无孤儿记录和字段类型兼容后安全补齐。
5. 任何未知结构、非法状态、孤儿记录或非完整索引仍必须在写入前被拦截。

## 优先级

高，上线阻断。

## Triage

- 推荐轨道：Standard
- 分类理由：
  1. 数据库 schema 变更：是
  2. 新增 API 端点：否
  3. 新外部服务集成：否
  4. 影响文件数：>3
  5. 高风险业务逻辑（支付/权限）：是，属于生产数据库升级门禁
- 人类决定：用户已授权 Dev → Prod 上线任务“全部按建议继续”；作为该任务的
  上线阻断修正继续按 Standard 执行，Prod 写入仍需最终单独授权。

## 已核对的 Dev 现状（只读）

- `agent_attachment` 45 行；5 个解析字段存在，其中 SHA/大小/页数使用早期可空定义。
- `agent_run` 389 行；10 行空 `state_reason`，2 行已删除旧记录使用
  `zombie_cleanup_2026_05_28`。
- `user_third_party_account` 5 行、`feishu_auth_session` 115 行；字段和索引正确，
  但字段物理顺序与一次性建表顺序不同。
- `feishu_operation_proof_consumption` 3 行；两个目标外键缺失。
- Dev 完整备份已创建并在隔离 MySQL 8 恢复，122 张表和核心行数核对通过。

## 硬约束

- 不删除、不更新任何现有业务行。
- 不把字段顺序差异当作结构错误。
- 只接受“最终结构”或已实证的 Dev 早期附件结构，不接受任意第三种结构。
- 关闭 `agent_attachment` 的启动时 AutoMigrate 隐形写路径；该表只允许显式评审
  migration 改结构。
- 空智能体状态只允许出现在 `running`；旧 zombie 标记只接受精确历史值且记录必须已删除。
- 飞书外键仅在无孤儿记录、父子字段类型完全兼容时补齐。
- 附件 5 个解析字段和飞书 proof 业务字段必须加入升级前、两次 migration 后以及
  后端完整启动后的逐行保护哈希。
- QA 不在范围内；Prod 保持只读直至最终授权。
