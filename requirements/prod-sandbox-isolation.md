# Prod 同机 Sandbox 隔离

## 来源
- 提出人：产品负责人
- 提出日期：2026-07-30

## 需求描述
将 Dev 已正常运行的 Sandbox、文件处理和技能执行能力部署到 Prod。Sandbox 与现有正式业务使用同一台云服务器，但必须做好隔离，不能让 Sandbox 故障、用户任务或后端 Docker 权限影响正式 API、MySQL、Redis、用户端和管理端容器。

## 业务目标
让正式客户能够完整使用首页 SOP、AI 智能体、插件技能及文档导出等依赖 Sandbox 的功能，同时保护 Prod 的用户资料、积分、业务记录和核心服务可用性。

## 优先级
高

## Triage
- 推荐轨道：Standard
- 分类理由：
  1. 数据库 schema 变更：否
  2. 新增 API 端点：待 S1/S2 评估，优先复用现有 Sandbox 接口
  3. 新外部服务集成：是，同机独立 Docker daemon / Sandbox 运行时
  4. 影响文件数：>3，涉及镜像构建、部署脚本、运行配置、安全检查和回归测试
  5. 高风险业务逻辑（支付/权限）：是，涉及生产宿主机容器控制权限和资源隔离
- 人类决定：确认 Standard，并明确使用同一台 Prod 云服务器

## 产品验收边界
- 正式 API 只能控制 Sandbox 专用运行时，不能控制 Prod 的 MySQL、Redis、前后端和管理端容器。
- Sandbox 容器不挂载 Prod 数据目录、配置文件、密钥或主 Docker socket。
- Sandbox 容器保持非特权、只读根文件系统、无业务内网访问，并限制 CPU、内存、进程数、执行时长和并发数。
- Sandbox 故障或资源耗尽时，SOP、聊天、登录、积分和数据库仍可正常服务；最坏只影响依赖 Sandbox 的代码/文件任务。
- 沿用已经验证的 `sandbox-skill:skills-v1.5.3` 能力，支持 pptx/docx/xlsx/pdf 等 Dev 已运行功能。
- 部署和回滚不能修改 Prod 用户资料、积分余额或历史业务记录。
- QA 环境不在本次范围；完成本地验证后进入 Dev 验收，再由产品负责人单独确认 Prod 部署。

## 备注
- Prod 当前约 7.4 GiB 内存、无 Swap；S1 必须给出保守的预热池、最大并发和资源预算，不能直接照搬 Dev 的 5 个预热容器。
- 会议副驾和说话人分离保持关闭，与本需求无关。
