# SOP / 智能体可见范围权限（实体视角）

## 来源
- 提出人：用户（产品 owner）
- 提出日期：2026-05-13

## 需求描述

原话：

> 需要添加一个功能，就是不管是智能体 chatbot 还是 SOP，需要增加一个显示的权限，如果客户在配置的时候应用了这个显示的权限，就代表它只想向某一些子用户展示，因此，他就需要勾选这个对应需要展示的子用户，而没有被勾选的子用户则在工作区看不到这个 SOP，或者是 chatbot。当然，如果用户没有应用这个显示的权限，那么默认向所有的子用户都展示。

结构化描述：

父账户在 SOP 模板 / 智能体（chatbot）的**编辑页内联**新增一个「可见范围」区块：

1. 默认状态：「全部子用户可见」（开关关闭）
2. 父账户可打开「仅指定子用户可见」开关，从弹窗勾选可见的子用户名单（范围 = 当前父账户名下所有子账号）
3. 未在白名单内的子用户在工作区**列表中看不到**该 SOP/chatbot
4. 已开始的运行 / 历史会话不受影响（仅过滤列表展示，不撤销已有访问）
5. 后期新增的子用户**默认看不到**已限制可见的 SOP/chatbot（白名单语义），需要父账户手动补勾

## 业务目标

1. **实体视角的快速配置**：父账户在创建/编辑一个新 SOP 或 chatbot 时，自然地决定"这个东西给谁看"，而不必再切到客户管理逐个子账号去配
2. **分发场景**：父账户经常一次性想把同一份资料/工作流只发给少数子账户（如某个客户线/某个团队），实体视角比用户视角效率高 10×
3. **保护现有用户体验**：默认 allow-all，老用户老 SOP 行为不变；只有主动打开开关才进入限定模式

## 优先级

中-高。是一个 UX 加速器，不阻塞业务；但父账户已多次反馈"用户视角弹窗逐个配置太繁琐"。

## Triage

- **推荐轨道：Standard**
- **分类理由**（5 条标准逐条）：
  1. 数据库 schema 变更：**是**（至少需要 `sop_template.visibility_restricted` + `chatbot_config.visibility_restricted` 两个字段；以及独立白名单关联数据，可能新增独立表或在现有结构上扩展）
  2. 新增 API 端点：**是**（至少 +2 端点：配置 SOP 可见名单 / 配置 chatbot 可见名单；列表查询接入新过滤）
  3. 新外部服务集成：**否**
  4. 影响文件数：**>3**（numind-server: 2 模型字段 + 1-2 store + biz/sop + biz/chatbot 的列表过滤 + 2 controller + migration + router ~ 8-10 文件；numind-web-v3: SOP 编辑页 + chatbot 编辑页加 UI 块 + 子用户选择器组件 + api 层 + 工作区列表的可见性过滤逻辑 ~ 6-8 文件）
  5. 高风险业务逻辑（支付/权限）：**是**（新增独立权限维度，且与现有运行权限叠加生效，错误会导致子用户漏看 / 误看资源）

## 与现有功能的关系（关键）

**重要：此功能与已上线的 `child-run-permission` 共存、互补，不替代。**

| 维度 | `child-run-permission`（已上线 2026-04-20） | 本需求 |
|------|---------|---------|
| 语义 | 运行权限（403 gate） | 可见范围（列表过滤） |
| 入口 | 客户管理 → 子账号弹窗（**用户视角**） | SOP/chatbot 编辑页内联（**实体视角**） |
| 默认值 | deny-all（手动开启） | allow-all（手动限制） |
| 数据表 | `user_template_permission` / `user_chatbot_permission` | 独立新表（建议：`sop_visibility_grant` / `chatbot_visibility_grant`，或统一 `entity_visibility_grant`，待 S2 决） |
| 控制层级 | 已运行/历史依然 403 | 仅列表展示，已运行/历史不变 |

**两层 gate 串行**：
- Step 1：可见范围过滤（本需求）→ 决定列表展示哪些
- Step 2：运行权限校验（现有）→ 决定列表里哪些能跑

**关键不变量**：被本需求过滤掉的 SOP，运行权限是否授予对它无意义（用户都看不到列表入口）；运行权限被授予但未在可见范围内的 SOP，列表仍不可见（白名单优先于运行权限授权）。

## 待 S1 探索的边界 case（先列、不锁）

- 父账户**关闭**「仅指定子用户可见」开关时，已勾选的白名单数据是否保留？（建议：保留，重新打开恢复同一名单；S1 brainstorm 验证）
- 子用户**从父账户名下被移除**时，其在白名单中的记录如何清理？（应级联清理）
- 子用户被**转移到其他父账户**时（如果产品支持）的清理逻辑
- 同一 SOP/chatbot 被多次编辑时，可见范围的 transaction 边界
- 已经开始的运行如果在中途被父账户撤销可见，**Run 详情页**是否还能进入？（用户原话："已开始的运行不受影响"——意即历史和运行中都可访问，仅工作区列表过滤；S2 spec 锁定）
- 管理端是否需要查看某 SOP/chatbot 的可见范围配置（admin 视角观察）
