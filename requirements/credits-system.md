# 积分计费系统（会员 + 积分 + 加量包）

## 来源
- 提出人：产品负责人
- 提出日期：2026-04-18

## 需求描述

将计费体系从旧的"会员阶梯制按次数"迁移到新的"会员 + 积分 + 加量包"体系。采用 Grandfathering 策略：旧会员在到期前沿用旧规则，新购会员和到期后用户统一进入新制。

### 旧制（现行）
| 等级 | 运行规则 | 时长 |
|------|---------|------|
| free | 不可运行 | — |
| trial | 10 次（总量） | 固定 3 天，¥9.9 |
| standard | 20 次/月 | 1-12 月 |
| premium | 无限次 | 1-12 月 |

### 新制（目标）
**会员机制：**
- 会员用户每月获得 **2000 积分**（月卡 ¥99，年卡 ¥949 含 20% 折扣，每月发放 2000）
- 积分用于扣减 AI 资源消耗（详见下方消耗点）
- 非会员（free）不可运行 SOP、不可购买加量包、不可使用积分

**加量包：**
- 规格固定：**¥29.9 购买 600 积分**（与会员积分单价接近，约 ¥0.0498/积分）
- 有效期：**3 个月**（从购买时刻计）
- **会员资格门槛**：只有当前有效会员才能购买和使用加量包；非会员购买入口不展示、接口拒绝
- 使用场景：会员当月积分耗尽后的续购救急

**扣减优先级：**
- 始终**先扣会员当月积分，再扣加量包积分**（避免加量包因 3 月过期浪费）
- 会员积分月底清零，加量包积分过期清零

### 积分消耗点（初步盘点，细则在 S1/S2 敲定）
| 场景 | 底层调用 | 备注 |
|------|---------|------|
| SOP 执行 | Chat + 可能 Vision + 文件解析 | 核心消费点 |
| 销售知识库对话（SalesRAG） | Embed + Rerank + Chat | |
| 卡片生成 | 需确认是否走 LLM | |
| 知识库 ingestion | OCR + Embed + 文件解析 | 上传文档时一次性消耗 |
| 独立 Vision / OCR / ASR | 对应单项服务 | |
| 图像生成（wanx2.1） | 按张计费 | 当前代码未调用，暂预留 |

**不消耗积分：** 鉴权、页面浏览、账单/会员中心、管理端操作。

### 准确估算机制（R2 路线）
- **扣减时机**：call 前预扣，call 后对账（多退少补）
- **估算算法**：基于 prompt 字符数 × 经验系数（汉字 ≈ 1.5 token）估算 prompt tokens；completion 侧使用"该模型历史平均 completion/prompt 比值"加权
- **目标精度**：±20% 内，防止会员被薅穿
- 不引入 tiktoken 等外部 tokenizer 依赖（避免多语言/多模型兼容问题）

## 业务目标
1. **营收模型清晰化**：积分制是 SaaS 行业通用语言，便于向客户讲清"你买了多少资源"
2. **防薅羊毛**：旧制"20 次/月"无视实际成本，重度用户（长 SOP、Vision 调用）会击穿毛利率；积分制按真实消耗扣减
3. **开辟第二条收入曲线**：加量包是会员之外的增量收入，解决"会员月底不够用又不想升级"的场景
4. **平滑迁移**：旧会员无感知（Grandfathering），不产生投诉和退款压力

## 备注

### 已确认决策（本次 Triage 前讨论已定）
- **D1（会员月度额度）**：**2000 积分/月**，已确认，基于成本预算反推（会员 ¥99 → 毛利率 80%）
- **D2（估算机制路线）**：**R2 字符数估算 + 事后对账**
- **D3（加量包定价）**：**¥29.9 / 600 积分 / 3 月有效期**，定价与会员单价接近
- **D4（扣减优先级）**：**会员积分优先，加量包次之**
- **D5（老用户策略）**：**Grandfathering**——旧会员到期前沿用旧规则，新购和到期后进入新制
- **D6（会员资格门槛）**：加量包仅限当前有效会员购买和使用

### 仓库影响
- numind-server：biz/credit、biz/sop 扣减路径、biz/billing、controller、store、migration
- numind-web-v3：购买页（加量包入口+会员资格判断）、积分余额展示（分会员/加量包两档+倒计时）、SOP 运行前估算展示
- numind-admin-web：定价规则管理（复用现有 AI Service 管理）、历史用户迁移工具、积分发放调试工具

### S1 需要明确的开放问题
1. 旧制用户的"未消费额度"处理策略（继续用完 vs 主动切换积分制的换算表）
2. R2 估算系数的初始值来源（基于历史 `usage_record` 做一次数据分析 spike，还是先上线固定系数再灰度校准）
3. 卡片生成是否走 LLM（若纯前端渲染则不消耗积分）
4. 加量包过期清理的定时任务归属（独立 cron vs 扣减时 lazy check）
5. 老会员是否需要"主动切换到新制"的入口（含换算规则）
