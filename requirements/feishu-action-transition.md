# 飞书授权后动作切换稳定性

## 来源
- 提出人：客户
- 提出日期：2026-07-20

## 需求描述
用户在 Agent 中执行飞书任务时，首次授权完成后，后续阶段可能没有自动展示新卡片；刷新后又会显示已过期的旧卡片，继续操作可能返回 `Parameter verification failed`。飞书业务操作不再要求任何二次确认。

## 业务目标
让每个用户创建的任意 Agent 都能稳定完成“需要授权 → 授权后继续 → 执行飞书操作”的流程，不依赖刷新页面，也不会让旧卡片误提交下一阶段。权限授权完成后直接执行飞书业务操作，不再进入确认阶段。

## 优先级
高

## Triage
- 推荐轨道：Standard
- 分类理由：
  1. 数据库 schema 变更：否
  2. 新增 API 端点：否
  3. 新外部服务集成：否
  4. 影响文件数：>3
  5. 高风险业务逻辑（支付/权限）：是（飞书授权与外部写操作确认边界）
- 人类决定：确认快速 Standard，并授权推进至 Dev；仅运行针对性回归和仓库强制检查，最终产品验收由客户执行。

## 备注
- 删除飞书业务确认卡片和主动 `waiting_confirmation` 流程；所有已在命令白名单内且通过账号、权限、作用域和幂等校验的命令直接执行。
- 不新增自动授权或自动确认机制。
- 飞书官方权限授权仍然保留；它不属于业务确认。
- 历史 `waiting_confirmation` 数据只保留兼容执行能力，避免部署时把已有任务留成死状态，不再生成新的确认态。
- 不在浏览器端持久化飞书授权 URL、设备码或凭据。
- 前端 Playwright 运行时诊断已尝试，但 Dev IP 被浏览器安全策略拒绝；根因由 Dev 服务端日志、持久化状态和代码链路交叉确认。
