# 飞书写入命令指引与纠错能力修复

## 来源
- 提出人：用户（Dev `agent_run #359` 客户问题）
- 提出日期：2026-07-29

## 需求描述
Agent 1 已完成 8 条小红书笔记分析，但连续 5 次构造飞书 Base 批量写入命令失败，所有失败均发生在执行前参数校验，飞书 API 没有收到任何写请求。用户确认实施以下范围：

1. 飞书命令连续可纠错次数由 5 次提高到 10 次。
2. 查明并修复 Agent 写错长命令的指引原因，而不是否定 Agent 构造长内容的能力。
3. 消除 `stdin_json` 在工具定义中可用、Command Catalog 中却拒绝的矛盾。
4. 保留由 Agent 自己构造完整 `--json` 命令，不引入“后台替 Agent 转换写入格式”。
5. 确保 Agent 在写入前看到明确、完整且互不冲突的批量写入与 CellValue 指引。
6. 增加不含敏感业务数据的诊断证据与客户回归测试。

用户明确排除：不修改最终用户提示文案（此前方案第 7 点）。

## 业务目标
- 让具备长内容生成能力的 Agent 获得唯一、准确、可执行的飞书 Base 写入契约。
- 避免工具 Schema、托管策略和技能参考文档互相矛盾导致无效纠错。
- 将同一纠错窗口的容错空间提高到 10 次，同时保留执行前安全校验。
- 后续同类问题能判断 Agent 实际读取了哪个 reference、在哪一类校验上失败，而不记录 Base token、正文或完整 JSON。

## 验收标准
1. 连续参数校验失败的第 1–9 次仍返回可纠错结果，第 10 次进入 exhausted，第 11 次不访问执行器。
2. 所有模型可见说明对 `stdin_json`、`@file` 与内联 `--json` 的支持范围一致，不再同时宣称互相冲突的用法。
3. Agent 仍直接生成 `base +record-batch-create ... --json <完整 JSON>`；服务端不替 Agent 构造或转换业务 payload。
4. Agent 1 第一次批量写入前被明确要求读取批量创建和 CellValue 两份指定 reference，且工具调用轨迹可安全识别读取的 skill/reference。
5. 参数校验失败可安全记录 run、工具、命令类别、失败分类、attempt/max_attempts、是否调用飞书；不得记录 token、正文、完整 argv 或 JSON payload。
6. `agent_run #359` 的核心场景有永久回归测试：8 条分析、分批写入规划、长内联 `--json` 契约可被正确指引和校验。
7. 不修改面向最终用户的汇总提示文案。
