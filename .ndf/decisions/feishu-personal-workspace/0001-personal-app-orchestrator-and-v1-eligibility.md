# ADR 0001：个人自建应用、连接编排器与首版准入边界

- 日期：2026-07-13
- 状态：Accepted
- 决策人：Michael
- 阶段：S1

## 背景

目标体验是复刻 Claude Code 驱动 lark-cli 的连接方式：用户只需告诉有数 Agent“连接飞书”，Agent 自动发起个人自建应用创建和后续权限申请；用户只在飞书官方页面确认，完成后原任务自动继续。

飞书授权同时包含应用权限和用户权限。用户权限支持按 scope 增量授权；企业自建应用的部分权限可能需要租户管理员审批。因此，个人自建应用路径无法保证覆盖所有普通企业员工。

## 决策

1. 不新增独立的飞书 Agent。现有有数 Agent 调用专用连接工具；后端连接编排器以确定性状态机管理建应用、授权、持久化、任务恢复和解绑。
2. 每个有数账号维护独立的个人飞书自建应用、CLI HOME、凭据、Token 和权限状态，禁止跨用户复用。
3. 权限采用渐进授权和执行优先策略：除系统已明确知道用户未连接外，收到飞书操作后先直接执行，不在每次调用前强制预检权限；只有飞书返回明确的未连接、权限不足或授权失效错误时，才申请当前能力所需的最小权限。
4. 配置完成后自动、幂等地重试触发配置的原 Agent 操作，不要求用户重新输入命令；重试成功本身就是能力验证，不额外增加阻塞式 API 探测步骤。
5. 首版只支持有权创建个人自建应用、并能完成所需租户管理员审批的用户。权限不足时明确引导联系管理员；首版不增加共享有数应用作为第二条连接路径。
6. 设置页只承担状态查看、重连和解绑，Agent 对话是主要连接入口。

## 理由

- 授权流程本质是可恢复的状态机，不需要第二个自主推理主体。
- 单一 Agent 保留原始任务上下文，能在授权后准确恢复操作，避免双会话、双状态源和重复推理。
- 渐进授权符合最小权限原则，也与用户期待的 Claude Code 体验一致。
- 限定首版准入人群可以先验证个人自建应用链路，避免同时建设个人应用和共享应用两套截然不同的安装、审批与运维体系。

## 后果

- 产品必须识别“无创建权限”“待管理员审批”“用户拒绝授权”“授权撤销”等不同状态，不能统一显示为连接失败。
- 产品状态中的权限信息是最近已知状态，只用于错误解释、设置页展示和避免已知无效调用，不能变成每次飞书操作前的强制网络预检。
- 首版可服务人群受限，连接入口必须提前说明准入条件。
- 后续若要覆盖普通企业员工，应另立需求评估共享应用、应用商店或租户管理员安装路径，不能偷偷改变本决策的账号隔离模型。
