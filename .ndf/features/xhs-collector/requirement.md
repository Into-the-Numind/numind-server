# 小红书选题采集插件 (xhs-collector)

## 来源
- 提出人：陈峙羽（产品 / 老板）
- 提出日期：2026-06-23

## 需求描述
把市面上（淘宝）售卖的「小红书自动创建选题库（电脑插件版 V3）」的**小红书采集能力**，移植成有数**自有的浏览器插件**，面向有数客户（小红书 IP 陪跑机构 / 操盘手）使用。

客户在自己**已登录小红书的浏览器**里浏览 / 搜索小红书，通过插件悬浮按钮**一键采集**笔记数据（标题 / 正文 / 封面 / 视频直链 / 评论 / 标签 / 作者 / 点赞 / 收藏 / 评论数 / 发布时间等），数据进入**有数的选题库 / 内容生产流程**，喂给内容生成 SOP。

**明确不做抖音**——抖音的解析重活在第三方服务端，属另一个量级的工程，单独立项。

## 采集字段（已锁，2026-06-23 确认）
原则：**能采到的全采**。评论同时存「评论数」和「评论内容」。

**笔记维度**
- 笔记 ID（去重主键，技术必需）
- 笔记类型（图文 / 视频）
- 标题
- 正文
- 标签
- 封面图（链接）
- 笔记链接
- 发布日期
- 视频链接（视频笔记；也是「视频文字稿」的前置，没它做不了 ASR）
- 视频文字稿（下游 ASR 派生）

**互动维度**
- 点赞数
- 收藏数
- 评论数
- 分享 / 转发数
- 评论内容（热门前 N 条，含评论文本）

**作者维度**
- 作者名
- 作者主页链接 / 作者 ID
- 作者粉丝数 ⚠️（「低粉爆款」判断用；粉丝数在作者主页不在笔记页，可能需多抓一步，实现成本 S2 评估）

**元数据**
- 采集时间（collected_at）

**采不到（不列入必采）**：阅读数 / 浏览量——小红书 web 端不公开（实测 `workReadedCount` 恒为 null）。
**范围注**：评论为页面加载出的热门前 N 条，非全量（全量需自动滚动，更慢且风控敏感）。

## 业务目标
- 给有数核心客户群（小红书 IP 陪跑）提供「一键把竞品 / 爆款笔记采进选题库」的工具，直接喂内容生产 SOP，形成「采集 → 选题 → 生产」闭环，提升产品黏性与差异化。
- 摆脱第三方工具的结构性问题：数据孤岛在飞书、卖家持有客户飞书密钥（安全隐患）、风控 / 维护不可控。改为有数自有、用有数登录态授权、数据落有数。

## 优先级
中-高（战略性产品功能，非紧急）

## Triage
- 推荐轨道：**Standard**
- 分类理由：
  1. 数据库 schema 变更：**是**（需新表存采集的选题 / 笔记 + migration）
  2. 新增 API 端点：**是**（需 ingest 端点接收插件上报数据）
  3. 新外部服务集成：**是（广义）**（全新浏览器插件工件；不含新付费外部服务）
  4. 影响文件数：**>3**（插件本体 + 后端 ingest/model/store + 前端选题库展示）
  5. 高风险业务逻辑（支付 / 权限）：**待定**（采集 / 视频转写 / AI 分析是否扣积分，S1/S2 定）
- 人类决定：**确认 Standard**（2026-06-23）

## 技术背景（逆向已完成）
- 已对购买的插件做代码级逆向。**小红书采集 = 纯客户端**：content script 扒 DOM（`section.note-item` / `.note-detail-container` / `.comment-item`）+ 注入 main world 读页面自身的 `window.__INITIAL_STATE__.noteDetailMap[noteId]` 取视频直链。**零签名逆向、零自己发请求、不经任何服务端**——白嫖真实登录浏览器已加载的数据，可完全自建。
- 抖音采集 = 混合（本地拿分享 URL + 卖家服务端 `prhy.gzonkj.com/api/parse` 解析），重活在服务端，**已排除**。
- 下游有数已具备：视频转写（`monitor/transcriber.go` + 会议副驾 ASR）、AI 分析（aiservice）、选题库（SalesRAG / SOP）。

## 待决项（S1 提案阶段解决）
1. **数据落地**：有数选题库 / SOP　／　客户飞书多维表格　／　两者都支持 —— 决定后端落库形态与前端展示。
2. **插件分发**：Chrome 应用商店上架（有审核 / 政策风险）　／　自托管签名安装引导 —— 影响客户安装体验。
3. **积分策略**：采集 / 视频转写 / AI 分析 是否扣积分、怎么扣。
4. **客户鉴权方式**：插件如何用有数登录态（粘贴 user_token / 其它）。

## 备注
- 长期成本：采集靠扒小红书 DOM / 状态，小红书改版会失效 → 持续维护税（因跑在真实登录态 + 人工节奏，塌的频率低、修起来快）。
- 合规：面向客户、各自用自己登录态、人工节奏触发，是数据采集里最可辩护的形态；仍属平台 ToS 灰区，需业务侧知悉。
