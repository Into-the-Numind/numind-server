# 需求卡片：semantic-chunk-reliability（语义切块可靠 + 可观测 + 好兜底）

> S0 · feature id: semantic-chunk-reliability · track: standard · 2026-06-17

## 1. 一句话

让知识库入库的切块"稳定走语义、兜底也切得好、永不让用户上传失败、全程可追溯"。

## 2. 背景（实证）

- 语义切块服务（`BAAI/bge-small-zh`，Python `semantic_server.py:9093`）**确实部署且健康**（dev+prod 实测 `/health` ok、`/split` 实测能切）。HybridSplitter 语义优先、固定长度兜底。
- 但 dev 历史 chunk 约 **7~8 成是固定长度兜底切的**（>2000 字，落在规则档 1500-6000 区；语义档是 500-2000）。用户上报"语义切分经常不工作"属实。
- **病根：兜底是静默的**——语义没就绪/失败时系统不记录、不告警、照样用固定长度切。**没人能测出真实兜底率，出问题无法定位。** 精确触发原因（启动窗口 / 单例状态未恢复 / `/split` 真失败）现在查不出来，正因为没有留痕。
- 切块器是启动单例（`biz.go:232`），`Split()`（`pipeline.go:170`）不带 strategy；`SplitWithDetails` 已能返回 strategy 但没被用。规则兜底块上限 6000 偏大。

## 3. 用户体验原则（客户定，最高优先级）

> 用户上传文档**只关心成功**,不关心后台用了语义还是兜底。**成功=没问题,失败=产品烂。**

优先级（严格按此）：
1. **首选**：稳定用语义切分。
2. **次选**：语义不行时,**必须成功 + 兜底要切得好**。**绝不**因语义挂了让上传失败。
3. **必做**：全程可追溯（记录每次走哪条路 + 为什么），出问题能定位修复。

## 4. Triage

**Standard**：① DB schema 变更（knowledge_document 加列存 strategy）② 动入库核心 ingest/pipeline ③ 影响文件>3。无新 API 端点 / 无新外部服务（语义已集成）。

## 5. 范围

- **In**：留痕（strategy+reason 持久化+日志）/ 永不失败加固+回归测试 / 改好兜底切块质量 / 适度提升语义可靠性（瞬时失败重试+周期重探）。
- **Out**：重切重嵌存量文档（独立后续，等留痕测出真实兜底率再决定）；语义模型升级；评估集（独立 feature）；前端改动（无）。

## 6. 验收标准（详见 PRD）

- AC1：每次入库,文档记录用了 `semantic` 还是 `rule_fallback`（+原因）,可查询、有日志。
- AC2：语义服务不可用时,上传**仍然成功**并产出 chunk（永不因切块失败而上传失败）,且留痕标记 `rule_fallback`。
- AC3：兜底切块产出的块大小合理（贴近语义档,不再动辄 6000 字大块）。
- AC4：语义 `/split` 瞬时失败先重试再兜底；语义崩溃恢复后能被重新启用（不必重启）。
- AC5：语义可用时稳定走语义（dev 实跑：传文档→strategy=semantic）。
- AC6：可用留痕在 dev 量出"真实兜底率"（为后续是否重切存量提供数据）。
