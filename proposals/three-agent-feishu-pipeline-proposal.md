# 三 Agent 飞书内容生产流水线 — 提案 + PRD

> Stage: S1 · Track: standard · Repos: numind-server（代码）+ numind-web-v3（审查后确认无代码改动） · Date: 2026-07-20  
> Predecessor: `requirements/three-agent-feishu-pipeline.md`（S0，commit `71590114`）  
> 权威业务规则：产品负责人提供的 Prompt 1 / Prompt 2 / Prompt 3 完整代码块

## §1 结论 [客户可见]

这三个 Agent 可以按已经确认的业务流程落地，而且不需要新增客户管理、飞书目标配置或 Agent 模板分发功能。

采用“现有 Agent Builder + Prompt 编排 + 最小工具补齐”的方案：

1. 在当前组织中，用现有 Agent Builder 创建并维护三个独立 AgentDefinition；不改造 `skill_template`，不向所有组织自动分发。
2. Agent 1 新增一个只读的 `xhs_note_list` 平台工具，自动读取当前登录用户自己的小红书选题库；工具分页上限为 100，不接受模型传入 `user_id`。
3. Agent 1 继续使用现有飞书工具查找、创建和更新当前用户的多维表格；飞书 Base 同时作为分析结果库和跨运行检查点，不在有数内部再建一套打标结果表。
4. Agent 2/3 复用现有上传、`file_read`、飞书 Docs/Base/Drive 工具和官方授权恢复流程。
5. 为满足 Agent 2“通读全部资料”，增强现有 `file_read`，让超过单次返回上限的内容可以按游标继续读取，而不是只返回前 200KB 后永久截断。
6. 三份 Prompt 在原有业务规则外补充统一的输入、目标解析、幂等、写入和续跑契约；不写死任何用户的飞书账号、文件 token 或链接。

## §2 已确认的产品决策 [客户可见]

| 决策 | 结论 |
|---|---|
| Agent 分发范围 | 只为当前组织配置三个 Agent；不升级官方模板系统 |
| 触发方式 | 用户进入对应 Agent 页面后手动用自然语言发起 |
| Agent 1 待处理范围 | 自动扫描未分析笔记，不要求用户手动勾选 |
| Agent 1 默认重分析 | 禁止；只有用户明确指定历史范围时才执行 |
| 小红书读取上限 | `xhs_note_list.limit` 最大值至少且本方案固定为 100 |
| Agent 1 产物归属 | 当前有数用户级共享的一个飞书 Base，跨该用户服务的多个客户复用 |
| Agent 2/3 产物归属 | 当前有数用户下的客户级飞书 Doc |
| 新客户 | Agent 2/3 分别创建新的客户画像文档、选题规划文档 |
| 同一客户 | Agent 2 更新同一份完整画像卡；Agent 3 在同一文档中新增轮次，指定修改某轮时更新该轮 |
| 飞书目标配置 | 不新增配置页；优先读当前对话上下文，缺失时询问用户 |
| 未授权飞书 | 复用官方授权流程，授权完成后恢复原任务 |
| 上传与飞书输入 | Agent 2/3 两条路径都支持，可以混合使用 |
| 内部客户实体 | 不新增；客户名称和目标链接来自当次对话上下文 |

## §3 方案比较 [客户可见]

### 方案 A：只补小红书读取工具

优点是代码最少。缺点是上传文件超过 200KB 后，Agent 2 只能看到前半部分，无法兑现 Prompt 中“通读全部资料”；长任务也缺少明确的检查点规则。

结论：不采用。功能看似可运行，但不完整符合权威 Prompt。

### 方案 B：Prompt 驱动 + 两处最小能力补齐

新增 `xhs_note_list`，增强 `file_read` 分段读取；其余全部复用现有 Agent、飞书和上传能力。Agent 1 按小批次完成分析和飞书批量写入，Base 是检查点；Agent 2/3 按统一目标解析规则读写客户文档。

结论：**采用。** 它完整覆盖业务流程，同时符合“不增加额外配置功能”的约束。

### 方案 C：新建后端固定工作流

由后端接管“扫描 → 调 LLM → 写飞书”的全部步骤，并新增任务表、状态表、客户表和目标配置。运行确定性更高，但业务判断会从 Prompt 移入专用代码，新增大量产品表面，也与已经确认的 Agent 主导方式冲突。

结论：不采用。

## §4 端到端业务流程 [客户可见]

```mermaid
flowchart LR
    A["用户采集小红书笔记"] --> B["有数：当前用户的小红书选题库"]
    B --> C["Agent 1：读取未分析笔记"]
    C --> D["逐条分析；分批提交"]
    D --> E["当前用户的飞书爆款素材库 Base"]
    F["客户上传资料 / 当前用户飞书资料"] --> G["Agent 2：通读并提炼"]
    G --> H["该客户的画像卡 Doc"]
    E --> I["Agent 3：读取合格爆款结构"]
    H --> I
    I --> J["该客户的选题规划 Doc；按轮次留痕"]
```

### 4.1 Agent 1

1. 用户说“按要求把还没分析的笔记打标”等自然语言指令。
2. Agent 检查当前对话是否已有目标 Base 链接或明确文件名；没有就询问一次，不猜测用户的文件。
3. Agent 使用当前用户身份在飞书中精确查找目标 Base：零个则创建，一个则复用，多个则要求用户提供链接或选择。
4. 未连接飞书或缺少 scope 时，现有 `lark_execute` 在真实业务操作前发起官方授权；成功后恢复同一个 Agent run。
5. Agent 读取目标 Base 中已有的 `小红书笔记ID + 分析状态`，形成已完成集合。
6. Agent 用 `xhs_note_list` 分页读取当前用户的选题库，计算未分析集合。
7. 每条笔记独立按 Prompt 1 分析；运行时按内容体量组成小批次，再用飞书批量写入。原子判断单位仍然是一条笔记。
8. 每成功写入一批，Base 就形成一个可恢复检查点。中断后再次运行，只继续剩余笔记。
9. 最终向用户报告已处理、已跳过、剩余和失败数量，不把“已开始”表述成“已全部完成”。

### 4.2 Agent 2

1. 用户必须提供或确认客户名称；可以上传资料、提供飞书链接，或两者同时提供。
2. Agent 逐份读完资料。上传文件若 `has_more=true`，必须继续调用 `file_read`，直到全部分段读完；不能在截断状态下声称已通读。
3. Agent 按 Prompt 2 区分一手陈述、第三方素材和半成品，生成一份完整最新版画像卡。
4. 目标文档优先取当前上下文链接；否则精确搜索 `【客户名称】客户核心信息与人群画像卡`。
5. 零个结果则创建，一个结果则整体更新为完整最新版，多个结果则询问用户。

### 4.3 Agent 3

1. 用户必须提供或确认客户名称，并提供 Agent 1/2 产物的链接或上传文件。
2. Agent 完整读取画像卡；读取爆款 Base 时只把字段完整的“达标”记录和可局部借鉴的“部分达标”记录放入候选集，“不达标”不得成为正式来源。
3. Agent 获取账号阶段、是否蓝 V、目标条数和上一轮反馈。账号阶段缺失按 0-1；蓝 V 缺失按非蓝 V；目标条数缺失按 70。
4. Agent 严格按 Prompt 3 生成“向内求 / 向外求”以及六大类选题，每条都带可追溯来源。
5. 目标文档优先取当前上下文链接；否则精确搜索 `【客户名称】选题规划`。
6. 新客户创建文档；同一客户默认追加新一轮，标题标明轮次和日期；用户明确要求修改某轮时只替换该轮。

## §5 统一身份、作用域与目标契约 [AI 内部]

### 5.1 三层作用域

| 层级 | 键 | 适用产物 | 规则 |
|---|---|---|---|
| 有数用户级 | `current_user_id`，只从鉴权上下文取得 | 小红书选题库、飞书授权、Agent 1 爆款 Base | 不允许工具参数覆盖；不同有数用户完全隔离 |
| 客户级 | `customer_name` + 当前用户提供/确认的文档链接 | Agent 2 画像卡、Agent 3 选题规划 | 一个有数用户可管理多个客户；不新增内部客户表 |
| 运行级 | `agent_run_id` | 当次输入、授权恢复、批次进度、最终报告 | 每次手动触发独立；外部写入沿用现有 operation 幂等和恢复机制 |

### 5.2 飞书目标解析顺序

三个 Agent 统一执行：

1. 当前用户在本轮明确给出的飞书链接；
2. 当前对话上下文中已经确认过的目标链接或文件名；
3. 若仍缺失，使用 `ask_user_question` 询问目标文件名或链接；
4. 对用户确认的名称执行当前飞书工作区精确搜索，并校验文件类型；
5. 结果为 0：按确认名称创建；结果为 1：复用；结果大于 1：要求用户提供链接或明确选择；
6. 不依赖长期记忆保证正确性，不把其他用户、其他客户或相似名称当作目标。

这套规则允许记忆系统提供便利，但正确性不依赖记忆系统是否命中。

### 5.3 授权契约

- Agent 不预先要求用户去设置页连接飞书。
- Agent 先尝试真实业务操作；现有平台层负责 scope preflight、授权卡、加密 operation 和恢复。
- 授权完成后恢复原 Agent run，不要求用户重新下指令。
- 所有身份、token、connection ID 和 CLI HOME 都由平台绑定，模型不可指定或读取。

## §6 Agent 1 数据契约 [AI 内部]

### 6.1 `xhs_note_list` 工具

只新增一个小红书工具，不新增 `mark_analyzed`，也不把飞书分析状态回写到有数的小红书表。

输入契约：

| 字段 | 类型 | 规则 |
|---|---|---|
| `cursor` | string，可选 | 稳定游标；空表示第一页 |
| `limit` | integer，可选 | 1-100；最大值固定 100，不使用 20 作为能力上限 |
| `xhs_note_ids` | string[]，可选 | 用户明确要求重分析指定笔记时使用 |
| `keyword` | string，可选 | 按标题/正文查找明确的历史范围 |
| `collected_from` / `collected_to` | RFC3339，可选 | 用户指定历史时间范围时使用 |

禁止输入 `user_id`。工具从 `middleware.UserIDFromCtx` 取得当前用户，再走带 `WHERE user_id = ?` 的现有 XHS store。

输出契约：

| 字段 | 说明 |
|---|---|
| `items[].id` | 有数内部笔记 ID，只用于本次工具定位 |
| `items[].xhs_note_id` | 跨运行、跨飞书记录的稳定业务键 |
| `items[].note_type` | normal / video |
| `items[].title` | 笔记标题 |
| `items[].content` | 笔记正文 |
| `items[].video_transcript` | 视频文字稿；确实未取得时为 null |
| `items[].like_count` | 采集到的点赞数 |
| `items[].collect_count` | 采集到的收藏数 |
| `items[].comment_count` | 采集到的评论数 |
| `items[].comment_texts` | 评论与一层回复的文本；不向分析 Prompt 暴露评论者身份推断能力 |
| `items[].note_url` | 小红书原文链接 |
| `items[].collected_at` | 采集时间 |
| `next_cursor` / `has_more` / `total` | 分页续读信息 |

工具不返回或不使用现有 `enrich_status` 作为本 Agent 的“已分析”判断。现有六个通用 AI 富化字段不是 Prompt 1 的完整结果，也不能替代飞书 Base 契约。

### 6.2 “未分析”与“重分析”定义

- **未分析**：当前用户的小红书库中存在该 `xhs_note_id`，但目标 Base 中不存在同一 `小红书笔记ID` 且 `分析状态=已完成` 的记录。
- **默认再次运行**：跳过所有已完成记录，只处理新增或未完成记录。
- **显式重分析**：只有用户在自然语言中给出笔记 ID、链接、关键词、采集时间范围或其他可验证范围时执行；更新原 Base 记录，不创建第二条。
- **范围模糊**：例如“重做之前那批”但无法唯一定位时，Agent 必须询问，不可自行扩大范围。
- **重复 Base 记录**：同一 `小红书笔记ID` 匹配多条时，不自动覆盖；报告数据异常并要求用户确认保留哪条。
- **内容后来发生变化**：默认仍遵守“不自动重分析”。只有用户明确要求时覆盖历史分析。

### 6.3 飞书 Base 标准字段

第一字段使用 `小红书笔记ID`，作为业务主键。字段总数低于飞书单表 100 字段上限，也低于 Agent 读取时 50 个投影字段上限。

#### 原始字段

| 字段名 | 类型 | 来源/规则 |
|---|---|---|
| 小红书笔记ID | 文本（主字段） | `xhs_note_id`；幂等比较键 |
| 有数笔记ID | 数字 | 有数内部 ID |
| 笔记类型 | 单选 | 图文 / 视频 |
| 笔记标题 | 文本 | 原始标题；缺失写“信息不足” |
| 笔记正文 | 多行文本 | 原始正文；缺失写“信息不足” |
| 视频文字稿 | 多行文本 | 原始转写；不适用或缺失写“信息不足” |
| 点赞数 | 数字 | 采集值 |
| 收藏数 | 数字 | 采集值 |
| 评论数 | 数字 | 采集值 |
| 评论区文本 | 多行文本 | 评论和回复按行整理；无可用文本写“信息不足” |
| 原文链接 | URL | 无链接写“未提供” |
| 采集时间 | 日期时间 | 有数采集时间；缺失留空 |

#### Prompt 1 分析字段

| 字段名 | 类型 | 允许值/规则 |
|---|---|---|
| 达标判定 | 单选 | 达标 / 部分达标 / 不达标 |
| 判定说明 | 多行文本 | 一句话证据；不只凭数据大小 |
| 原生赛道 | 文本 | 内容本身赛道 |
| 适配赛道 | 多选 | 房产 / 留学 / 移民 / 保险 / 求职 / 雅思 |
| 人群画像 | 多行文本 | 写到具体处境；资料不足则到可验证颗粒度 |
| 标题钩子 | 多行文本 | 爆款结构 1/5 |
| 开头留人 | 多行文本 | 爆款结构 2/5 |
| 正文结构 | 多行文本 | 爆款结构 3/5 |
| 情绪调动点 | 多行文本 | 爆款结构 4/5 |
| 结尾CTA | 多行文本 | 爆款结构 5/5 |
| 主语身份 | 单选 | 自己 / 客户 / 第三方 / 泛人称 |
| 六大类标签 | 多选 | 人设型 / 泛流量型 / 垂直人群泛话题 / 精准选题 / 硬广营销类 / 其他 |
| 子类标签 | 多选或文本 | 使用 Prompt 1 固定命名，可多选 |
| 能否跨赛道 | 单选 | 能 / 部分能 / 不能 |
| 跨赛道理由 | 多行文本 | 一句话说明 |
| 可借鉴部分 | 多行文本 | 明确后续可以借什么 |
| 不可照搬部分 | 多行文本 | 明确哪些行业、人物、事件或结果不能借 |
| 推导链 | 多行文本 | 一句话串联整体判断 |

#### 检查点字段

| 字段名 | 类型 | 规则 |
|---|---|---|
| 分析状态 | 单选 | 只在完整记录写入成功后设置“已完成” |
| 分析完成时间 | 日期时间 | 飞书成功写入时刻 |
| 分析规则版本 | 文本 | 三 Agent Prompt 版本；版本变化不触发自动重分析 |

### 6.4 原子性与批处理

- Prompt 1 的“一次只分析一条”解释为一条笔记是独立判断、独立字段集合，不能把多条合并成一个综合结论。
- `xhs_note_list` 能力上限是 100；Agent 可以根据正文长度分成若干分析批次。工作批次大小不是产品硬限制，也不改变“一次运行处理所有可处理未分析笔记”的目标。
- 飞书写入优先使用现有 Base batch-create / batch-update；每个批次中的每一行必须已经包含完整字段。
- 一批成功后才计入完成数。业务写入结果未知时不盲目重试；下一次先读 Base，以 `小红书笔记ID` 核对是否已经成功。
- 运行达到上下文或 turn 安全阈值时，必须如实报告剩余量；下一次运行依靠 Base 检查点续跑。

## §7 Agent 2 数据契约 [AI 内部]

### 7.1 输入

| 输入 | 必需性 | 规则 |
|---|---|---|
| 客户名称 | 必需 | 当前上下文缺失时询问，不从资料标题猜成最终名称 |
| 客户资料 | 至少一份 | 上传附件、飞书 Docs/Wiki/Base 或其组合 |
| 账号阶段 | 可选 | 明确为 0-1 / 1-10 时使用；缺失默认 0-1；不得自行判断 |
| 目标画像文档 | 可选 | 链接优先；缺失按统一目标解析 |

每份来源保留：来源文件名/标题、链接或附件标识、来源类别、实际读取完整性。只把已全部读取的资料标记为“已通读”。

### 7.2 输出

飞书 Doc 必须保持 Prompt 2 规定的标题和层级：

1. 资料来源判断：一手陈述 / 第三方素材 / 半成品素材；
2. 账号定位素材：不可替代微观动作、初步定位方向；
3. 核心人群画像：整体画像、按证据增加的细分人群；
4. 向内求素材库：来路、信念、代价、日常、价值观、专业观点、案例、证言/好评；
5. 第三方素材说明；
6. 深度看见候选点；
7. 资料缺口清单。

Agent 2 每次写入的是一份**完整最新版**，不是只追加本次差异。每个判断必须可回溯到来源；不生成选题、正文、口播稿或深度看见成稿。

### 7.3 文档命名与更新

- 默认标准名：`【客户名称】客户核心信息与人群画像卡`。
- 同一客户再次运行：读取原文档和新增资料，重新形成完整卡片后整体更新同一文档。
- 若用户明确给出不同文件名，以用户本轮确认的名称为准。
- 多个同名文档不自行选择。

## §8 Agent 3 数据契约 [AI 内部]

### 8.1 输入

| 输入 | 缺失行为 |
|---|---|
| 客户名称 | 询问用户 |
| 客户画像卡 | 询问链接/附件；不得只凭聊天印象生成 |
| 爆款素材库 | 询问 Base 链接/附件；不得退回模型常识假装是爆款库 |
| 账号阶段 | 默认 0-1 |
| 是否蓝 V | 按“否/未提供”处理，跳过全部硬广营销类 |
| 目标条数 | 默认 70；资料不足时允许少于目标，不得降质凑数 |
| 上一轮反馈 | 有则先复述本轮规避重点 |
| 目标选题文档 | 按统一目标解析 |

### 8.2 爆款来源准入

- “达标”：优先进入正式候选集。
- “部分达标”：可以使用，但每条必须标注“仅借局部手法”，并遵守 `可借鉴部分 / 不可照搬部分`。
- “不达标”：禁止作为正式来源。
- 缺少达标档位、标签、跨赛道结论或原文链接：只进入待确认，不计正式数量。
- 目标客户的事实、经历、案例、评价、结果和观点只能来自画像卡；爆款库只提供结构、打法和有链接的参考。

### 8.3 每条正式选题字段

| 字段 | 规则 |
|---|---|
| 选题内容 | 标题方向 + 一句话说明讲什么 |
| 选择原因 | 一句话说明为什么适合该客户；这是原具体输出模板遗漏、现补齐字段 |
| 归属小类 | 使用 Prompt 3 固定六大类/子类命名 |
| 生成路径 | 向内求 / 向外求 |
| 推导链 | 客户素材 → 焦虑/欲望/顾虑/决策问题 → 值得讲的理由 |
| 参考来源链接 | 除允许独立生成的硬广-好评型外，正式选题必须有链接 |
| 参考类型 | 结构+内容 / 仅参考结构 / 无，独立生成 |
| 变形说明 | 向外求必填且说明人群、场景、具体料、不可照搬项；向内求为“-” |
| 主语自检 | 人设型必填；其他为“-”；0-1 阶段必须是创始人/顾问本人 |

### 8.4 文档结构与轮次

- 默认标准名：`【客户名称】选题规划`。
- 文档内每轮使用 `第 N 轮｜YYYY-MM-DD｜账号阶段｜蓝V状态` 标题。
- 新一轮追加完整的：本轮规避重点（如有）、六大类选题、数量统计、待确认清单。
- 用户明确要求修改第 N 轮时，只替换该轮对应块；无法唯一定位则询问。
- 不输出完整正文、口播稿或小红书成稿。

## §9 权威 Prompt 的两处补丁 [客户可见]

逐段对照原始代码块后，确认有两处内部要求和具体输出模板不一致，本方案按“更严格且更靠前的要求”补齐：

1. Prompt 1 核心目标要求说明“后续借鉴时应该借什么、不能照搬什么”，但输出表格没有对应行。正式 Agent 1 增加 `可借鉴部分`、`不可照搬部分`，同时进入 Base 契约。
2. Prompt 3 的“每条选题必须包含”要求 `选择原因`，但后面的具体选题模板漏写。正式 Agent 3 每条固定增加 `选择原因`。

除这两处补齐外，不重新定义六大类、子类、达标规则、账号阶段、蓝 V、向内求/向外求或禁令。

## §10 已发现的数据限制 [客户可见]

### 10.1 数值 0 与“未采集”目前不可区分

现有小红书摄入结构把点赞、收藏、评论数保存为非空整数。插件如果没有传某个数字，后端得到的也是 `0`，因此历史数据无法可靠区分“真实为 0”和“未采集”。这与 Prompt 1 的“缺失写信息不足”存在一个原始数据层限制。

本 feature 的处理原则：

- Agent 不猜测数值；工具只把库中保存的数值标为“采集值”。
- 标题、正文、视频稿、评论文本、链接等能够判空的字段严格使用“信息不足/未提供”。
- 不在本 feature 中为了这一点改造采集插件和历史数据库，因为这会扩大到采集协议、前端展示和历史回填，且无法恢复历史真实缺失状态。
- 若未来业务必须区分“0”和“未采集”，单独升级采集协议为 nullable/presence-aware，并只对升级后的新数据提供准确区分。

这不会阻塞三个 Agent，但验收时不能把历史 `0` 宣称为“已证明真实为 0”。

### 10.2 评论只是采集到的有限样本

Agent 只能分析选题库中保存的评论及回复，不能推断完整评论区，也不能猜测评论者身份。所有“评论区信号”结论都应表述为“基于已采集评论”。

## §12 风险与控制 [AI 内部]

| 风险 | 控制 |
|---|---|
| 100 条完整正文一次进入上下文过大 | 工具上限仍是 100；Prompt 允许 Agent 按正文体量用更小工作批次，分批写入后释放进度压力 |
| 长任务达到 100 turns / 上下文上限 | Base 每批形成检查点；如实报告 remaining；再次运行自动续跑 |
| 飞书写入响应未知 | 沿用现有 unknown-write fence，不盲重试；下一次先读 Base 核对业务键 |
| 重复运行制造重复行 | 每批写入前按 `小红书笔记ID` 比对；显式重分析执行 update，不 create |
| 同名飞书文件 | 精确搜索仍大于 1 时询问用户，不按时间或相似度猜测 |
| 上传大文件只读到前半段 | `file_read` 游标续读，只有 `has_more=false` 才标记通读完成 |
| Agent 2 把第三方/半成品写成客户事实 | 输出中保留来源分级和依据；第三方只佐证，半成品不可照抄 |
| Agent 3 为凑 70 条编造 | 资料不足允许少于目标；原因写入数量统计和待确认清单 |
| 部分达标素材被整体照搬 | 强制使用 Agent 1 的可借鉴/不可照搬字段，并标注“仅借局部手法” |
| 两个有数用户串数据 | XHS 工具无 `user_id` 输入，file_read 所有权校验，飞书平台身份绑定；跨用户访问返回不存在/拒绝 |
| 用户同时启动两个 Agent 1 run | v1 产品语义要求同一用户串行触发；Base 无唯一约束，真正并发写存在竞态。若真实使用中需要并行运行，再增加用户级运行租约，不能靠 Prompt 假装绝对互斥 |

## §13 AI 可观测性 [AI 内部]

本 feature 使用现有 Agent ReAct LLM trace，不新建独立 LLM 调用链。

- Trace 根：现有 `agent_run` trace，保留 `agent_run_id`、`agent_definition_id`、当前用户内部 ID。
- 新 Span：`tool.xhs_note_list.execute`，记录过滤类型、limit、returned_count、has_more、耗时；不把笔记正文或评论写入 metadata。
- 扩展 Span：`tool.file_read.execute` 增加 offset、returned_bytes、has_more、next_offset；不把客户文档内容写入 metadata。
- 飞书读取、创建、更新继续使用现有 `lark_execute` operation 观测链路。
- Agent 1 最终 trace metadata 增加 processed/skipped/remaining/failed 计数；Agent 2/3 增加 input_source_count 和 output_mode（create/update/append/replace-round）。
- 客户名称、客户资料正文、评论原文和飞书 token 均不进入 trace metadata。
