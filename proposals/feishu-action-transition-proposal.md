# 飞书授权后动作切换稳定性 — 提案

## §1 方案概述 [客户可见]
保留飞书官方授权，但彻底取消有数自己的飞书业务确认步骤。用户完成权限授权后，Agent 直接继续原任务。平台仍校验当前有数用户、飞书账号、应用、授权会话、Agent 任务、工具调用、命令白名单、权限范围与幂等键；只是不会再弹出“是否确认执行”的第二张卡片。

部署前已处于历史确认状态的任务不会被丢弃：再次恢复时直接按原始、加密保存的命令执行，浏览器不能修改命令内容。旧授权卡片误发 `user_completed` 时也按当前服务器状态恢复，不再返回参数错误。

## §3 技术可行性 [AI 内部]
### 现有功能复用
- 复用 Feishu Operation 的账号代际、命令目录、权限预检、加密请求、执行租约与幂等机制。
- 复用现有授权会话和 Agent continuation，不新增 API、数据库字段或第三方依赖。
- 复用已有 `waiting_confirmation` 状态作为只读历史兼容入口，不再产生新记录。

### 技术风险
- 高风险写操作不再等待人工确认，可能产生用户未预期的修改。此风险由客户明确接受。
- lark-cli 某些命令仍要求 `--yes`；该参数必须由服务器在执行时按命令目录追加，不能由模型或浏览器提供。
- 部署时可能存在历史确认态；必须保证其只执行一次，并继续使用原有加密请求和幂等栅栏。
- 授权完成与 Agent 恢复并发时，旧卡片可能迟到；后端必须按当前持久化状态解释动作，不能相信卡片阶段。

## §4 产品需求定义 — PRD [AI 内部 — 不要为可读性简化]
### 用户故事
- 作为任意 Agent 的用户，我完成飞书官方授权后，需要原任务直接继续，而不是再做一次有数业务确认。
- 作为处于旧会话或旧页面的用户，我点击旧授权卡片后，平台需要根据服务器当前状态恢复，不应返回 `Parameter verification failed`。
- 作为平台运维者，我需要历史确认态在升级后安全地、幂等地继续，不能丢任务或重复执行。

### 验收标准
- [ ] 新建的任何飞书业务操作都不会返回 `phase=confirmation` 或进入新的 `waiting_confirmation`。
- [ ] 需要 `--yes` 的 allowlisted 命令由服务器自动追加，并且只执行一次。
- [ ] 历史 `waiting_confirmation` 操作调用恢复后直接执行；重复恢复不会重复调用 CLI。
- [ ] 当前状态已不是授权态时，旧卡片提交 `user_completed` 不再返回参数校验错误。
- [ ] 前端不再展示飞书业务确认按钮或确认文案；飞书官方授权卡片维持不变。
- [ ] 不新增 API、DB schema、浏览器凭据持久化或自动授权。

### 边界情况
- 授权完成后命令仍缺少另一组权限：继续展示下一张官方授权卡片，不进入业务确认。
- 历史确认操作已成功但 Agent continuation 丢失：只补发已存结果，不重放飞书命令。
- 历史确认操作正在执行：加入现有执行/租约流程，不启动第二次执行。
- 页面仍持有旧 `user_auth` 卡片，但服务器已进入历史确认态：将其视为恢复信号，按服务器状态直接继续。
- 页面仍持有旧 confirmation 卡片：确认动作作为滚动升级兼容恢复；取消动作仍尊重用户明确取消。

### 权限规则
- 只允许当前登录用户操作其当前 generation 下的 operation。
- 浏览器只能提交 operation_id 和固定动作，不能提交 argv、scope、App ID、用户 ID 或 Agent 任务 ID。
- 命令必须通过服务端 catalog 白名单、作用域预检和加密请求完整性校验。

### UI 行为规格
- 页面位置：Agent 对话时间线中的飞书外部动作卡片。
- 布局要求：不新增组件；删除 confirmation 展示分支，保留创建应用、用户授权、管理员授权及其 loading/error/success 状态。
- 交互模式：用户只对飞书官方页面操作点击“我已完成，继续”；业务命令自动继续。
- 状态处理：授权处理中保持已有进度样式；授权失败提供重试；执行成功或失败沿用 Agent 工具结果；不显示任何业务确认卡片。

## 产品级方案比较与已确认结论

### A. 只修前端卡片（最小改动）
- 优点：改动最少。
- 缺点：确认阶段仍存在，旧/新状态竞态仍可能重现，不能满足“彻底删除确认”。

### B. 删除主动确认阶段并保留历史兼容（采用）
- 优点：新任务流程最短；保留账号、权限、catalog、幂等和加密边界；升级时不会遗留死任务。
- 缺点：需要同时修改后端执行入口、生命周期兼容和前端展示。

### C. 删除所有确认相关状态、API 与历史兼容
- 优点：代码表面最纯粹。
- 缺点：部署瞬间会让数据库中的历史确认任务失去恢复路径，滚动升级客户端也会报错，风险和工作量都不必要。

客户已明确选择 B，并明确接受不再进行飞书业务确认的产品风险。
