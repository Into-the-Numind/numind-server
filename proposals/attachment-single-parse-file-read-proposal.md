# 上传附件单次解析——产品方案

## 决策

保留 `file_read`，并把它确定为模型读取附件正文的唯一接口。上传后的后台任务负责一次性生成规范正文并持久化；Agent 对话只携带附件引用，模型需要内容时调用 `file_read` 从缓存分页读取。

## 为什么保留 file_read

直接把解析全文随每次消息附到模型上下文虽然看起来少一次工具调用，但会在用户没有要求阅读时也消耗上下文，并失去分页、读取状态、权限审计和大文件控制。`file_read` 能让 Agent 自主决定何时读取，并让每一页保持稳定、可恢复和可观测。问题不在工具存在，而在工具没有复用上传阶段已经产生的结果。

## 用户流程

```text
选择文件 → 上传 COS + 创建附件记录 → 后台解析一次 → 保存规范正文
    ↓                                        ↓
前端发送 attachment_id              Agent 收到附件引用
                                             ↓
                                  file_read 按需读取缓存并分页
```

若 Agent 在后台解析完成前发起读取，工具返回“处理中，请重试”的软结果；Agent run 不会因此异常终止。解析终态失败则返回固定失败类别，不暴露内部错误。

## 数据与兼容

- `parsed_content` 保存标准化 UTF-8 正文；`text_fallback` 继续服务旧路径和人类可读的包装说明，两者职责分开。
- `parsed_content_sha256` 是分页 continuation token 的单一来源。
- 历史成功附件以既有 `text_fallback` 做一次兼容回填，避免发布后立刻重算；之后的新解析保存原始正文。
- 历史前端仍可传 URL；若 URL 对应当前用户附件记录，`file_read` 自动命中同一缓存。
- `agent-outputs` 没有附件记录，继续走现有受控 URL 解析链路。

## 安全边界

附件 ID 使用 `id + current_user_id` 查询，URL 使用数据库归属或 URL 路径中的 current-user 校验。缓存不进入 tracing、日志或前端，只返回给当前 Agent 工具调用。COS presign、SSRF 防护、64 KiB 分页上限和 read token 校验全部保留。

## 发布顺序

1. 数据库 migration 与后端先部署，兼容新旧请求。
2. 验证后端健康和 migration 字段。
3. 前端再部署，切换为 ID 优先发送。
4. Dev 完成真实上传/请求契约检查；Prod 不在本次范围。
