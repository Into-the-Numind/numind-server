# 飞书技能参考文件简称安全解析 — 提案

## §1 方案概述 [客户可见]
Agent 不再需要记住 `references/style/...` 这样的内部完整地址。它可以提交官方参考文件的文件名简称，平台只在当前技能主页已经声明的参考文件中查找；唯一命中时自动换成标准完整地址，零命中或多命中时安全拒绝。用户的飞书账号权限、业务命令白名单和服务器文件隔离保持不变。

预期效果：类似 `lark-doc-update.md` 的合法简称一次成功，Agent 不会因目录前缀格式进行无意义重试；目录穿越、绝对路径、跨技能资源和任意文件读取仍然不可用。

## §2 报价与周期 [客户可见]
- 预估工作量：0.5 天以内
- 报价：包含在本次产品开发中
- 交付时间线：2026-07-19 部署 Dev

## §3 技术可行性 [AI 内部]
### 现有功能复用
- 复用 `declaredSkillReferences` 生成的当前技能动态白名单。
- 复用 `validSkillReference` 对标准完整引用做严格语法校验。
- 复用 `SkillReader.Read` 的 run/cursor/receipt 绑定与固定 CLI 资源校验。
- 复用 `containsExactString` 的标准地址精确匹配路径。

### 方案比较
1. **直接取消完整地址校验**：最快，但会扩大服务器资源读取面，拒绝。
2. **在已声明引用中做唯一 basename 匹配**：既让路径对 Agent 隐形，又维持 fail-closed，采用。
3. **为每份参考文件建立新的稳定操作 ID 注册表**：长期最强，但需要同步官方技能版本、注册表和更多维护机制，本次范围过大。

### 技术风险
- 不同目录可能存在同名文件：多命中必须拒绝，不猜测。
- 简称可能包含斜杠或目录穿越：简称模式只接受单一安全 basename。
- 官方主页变化：每次调用仍重新读取主技能并从当前内容派生白名单，不缓存陈旧名单。
- 完整标准地址兼容性：已有 `references/...` 调用继续走原有精确校验。

## §4 产品需求定义 — PRD [AI 内部 — 不要为可读性简化]
### 用户故事
- 作为任意有数 Agent 的用户，我需要 Agent 能用官方参考文件简称加载说明，以便飞书任务不因内部目录格式失败。
- 作为平台安全负责人，我需要简称解析仍被当前技能声明的参考文件集合限制，以便不扩大任意文件读取能力。

### 验收标准
- [ ] `reference="lark-doc-update.md"` 在 `lark-doc` 唯一声明该文件时成功解析到 `references/lark-doc-update.md`。
- [ ] 已有完整标准地址继续成功，行为不变。
- [ ] basename 在当前技能中不存在时，在执行参考文件 CLI 命令前拒绝。
- [ ] basename 在当前技能中存在多个同名候选时拒绝，不选择任一候选。
- [ ] `../x.md`、绝对路径、反斜杠、空值、带目录的非标准简称及非 ASCII 路径继续拒绝。
- [ ] 简称不能跨技能命中其他技能的参考文件。
- [ ] cursor 仍严格绑定调用方原始 reference 语义，不能借简称/全称切换绕过。
- [ ] 现有 receipt、run、CLI 版本和内容摘要边界不变。

### 边界情况
- 同一个 basename 位于两个子目录。
- 合法完整路径与非法路径具有相同 basename。
- 主技能只声明脚本或跨技能链接，不得进入引用白名单。
- 简称输入超过路径长度上限。
- 并发读取同一简称不共享可变状态。

### 权限规则
- 所有启用飞书工作区的 Agent 均可读取相同的官方静态说明。
- 本改动不读取用户飞书身份，不授予任何飞书业务权限。
- 真正的 Docs/Base/Wiki/Drive 操作仍由 `lark_execute` 做当前用户隔离、scope 检查和命令白名单验证。

### UI 行为规格
- 页面位置：无前端改动。
- 布局要求：N/A
- 交互模式：N/A
- 状态处理：合法简称不应产生工具错误；非法或歧义简称仍返回安全、无路径泄露的工具错误。
