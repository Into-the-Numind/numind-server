# 飞书授权成功后原任务恢复失败 — 提案

## §1 方案概述 [客户可见]
按固定版本飞书 CLI 的真实返回契约修正权限检查：只有在退出码、`ok`、已授权权限集合和缺失权限集合彼此一致时才继续原任务。授权全部通过时，官方返回的 `missing: null` 被解释为“没有缺失权限”；其他不完整或矛盾结果继续安全拒绝。

## §2 报价与周期 [客户可见]
- 预估工作量：当天完成
- 报价：项目内部缺陷修复，不单独报价
- 交付时间线：完成回归、全量检查、合并并部署 Dev

## §3 技术可行性 [AI 内部]
### 现有功能复用
- 复用 `ControlledScopePreflight`、命令目录权限集合、既有 operation 恢复和幂等机制。

### 技术风险
- 误把畸形 JSON 当作授权成功：通过字段存在性、退出码、完整集合分区和未知字段拒绝规避。
- 授权后重复写入：不改变 operation claim、attempt 和 terminal fencing，仅修正业务执行前的权限谓词解析。

### AI 可观测性
- 涉及 LLM 调用：否。仅修复既有 Agent 外部工具恢复前的权限检查。

## §4 产品需求定义 — PRD
### 用户故事
- 作为已完成飞书授权的用户，我需要原 Agent 任务自动继续，以便无需重复点击或重新发送提示词。

### 验收标准
- [ ] 官方成功响应 `ok=true, granted=<全部请求权限>, missing=null` 返回全部已授权。
- [ ] 官方部分缺失响应继续产生精确授权卡片。
- [ ] 官方未登录/无 token 响应安全映射为全部请求权限缺失，不泄露 CLI 诊断。
- [ ] 缺字段、未知字段、冲突分区、错误退出码继续 fail closed。
- [ ] 授权后原 operation 只恢复一次；业务写入前检查不再产生临时失败。
- [ ] `go test ./...`、Feishu race gate 和 `task lint` 通过。

### 边界情况
- `missing` 缺字段与显式 `null` 必须区分；只有官方允许的显式 `null` 可作为空集合。
- `granted`/`missing` 重叠、遗漏或包含目录外 scope 时拒绝。

### 权限规则
不改变用户隔离、Agent 隔离、scope 目录、操作幂等或写确认规则。

### UI 行为规格
不改前端；成功时现有授权卡自动进入原任务结果，失败仍使用现有安全错误展示。
